Security Assessment Report

Client-side Security Review: Anonymous Student Confession Portal

Overview & File Information

This website is an anonymous student confession portal where users can submit messages that are forwarded directly to Telegram. While the website advertises anonymity, inspection of the client-side source code reveals that sensitive implementation details and user data collection mechanisms are exposed.

Because all JavaScript executes in the user's browser, anyone can inspect the source code using Developer Tools and view hardcoded credentials, API endpoints, and data collection logic. This demonstrates why secrets should never be embedded in client-side applications.

1. Static Analysis

For this assessment, I reviewed the application's HTML and JavaScript without interacting with the backend.

Hardcoded Telegram Credentials

The source code contains a Telegram bot token directly inside JavaScript.

[ Screenshot of the BOT_TOKEN variable ]

Because JavaScript is downloaded to every visitor's browser, anyone can reveal this token by using:

  • Inspect Element
  • View Page Source
  • Browser Developer Tools

Exposing a bot token may allow unauthorized individuals to interact with the Telegram bot depending on its configuration.

Hardcoded Chat IDs

The application also exposes Telegram Chat IDs used for message forwarding.

[ Screenshot of Hardcoded Chat IDs ]

This reveals where submitted messages are being delivered and exposes internal implementation details that normally should remain server-side.

Direct Telegram API Calls

Instead of sending submissions to a backend server, the website directly communicates with:

https://api.telegram.org/bot<TOKEN>/sendMessage

This means every visitor can observe exactly how messages are transmitted.

[ Screenshot of fetch() function ]

Client-side Data Collection

The JavaScript collects various information from visitors including:

  • Screen resolution
  • Device memory
  • CPU core count
  • Browser language
  • Time zone
  • GPU information (WebGL)
  • Network information
  • Battery status (where supported)
  • Persistent device identifier stored in Local Storage
  • Approximate location from IP lookup
  • GPS coordinates if permission is granted

2. Security Findings

A. Exposure of Secrets

The Telegram Bot Token is embedded directly into client-side JavaScript.

Risk: Anyone inspecting the webpage can obtain the token and potentially misuse the bot.
Recommendation: Bot tokens should always remain on a secure backend server.

B. Client-side Logic Exposure

Since the entire application logic executes inside the browser, users can easily understand how messages are sent, what information is collected, and which Telegram channels receive data.

Key Takeaway: Sensitive operations should not occur entirely on the client side.

C. Personal Data Collection

Although the website is presented as anonymous, the code collects multiple pieces of device and browser information before forwarding data to Telegram (e.g., fingerprint info, persistent IDs, IP/GPS location, hardware specs, ISP data).

Risk: Collecting this information reduces the level of anonymity users expect.
Recommendation: Developers should clearly disclose what information is collected and ensure compliance with applicable privacy laws and institutional policies.

D. Device Fingerprinting

The application creates a persistent identifier using Local Storage:

localStorage.setItem(...)

Risk: This identifier remains on the device and can associate multiple submissions originating from the same browser.

3. Privacy Considerations

Anonymous submission platforms often encourage users to believe their identity cannot be linked to submissions. However, this application collects additional metadata that could potentially be associated with users (device characteristics, network info, fingerprinting, persistent IDs, location data).

Developers should ensure users are informed about any collected data and follow applicable privacy requirements.

4. Recommendations

  1. Move Telegram API requests to a backend server.
  2. Never expose Telegram Bot Tokens in client-side JavaScript.
  3. Store secrets using server-side environment variables.
  4. Minimize collection of user metadata; only collect what is strictly necessary.
  5. Publish a transparent privacy notice explaining what information is collected and why.
  6. Regularly rotate compromised API credentials if exposure occurs.

5. Conclusion

This analysis demonstrates several common security issues found in client-side web applications. The most significant issue is the exposure of sensitive Telegram credentials through hardcoded JavaScript, allowing anyone to discover the bot token by inspecting the page source. Additionally, the application performs extensive client-side collection of device and browser metadata before forwarding submissions to Telegram, which may conflict with users' expectations of anonymity.

Overall, the project serves as a practical example of why secrets should never be stored in frontend code and why developers should carefully consider the privacy implications of collecting user information in anonymous platforms.
